Why today matters. A table can only answer questions about things at least as detailed as one of its rows. A table with one row for each ride cannot say which customers cancelled, because a customer who never rides has no row. A table with one row for each customer each month cannot say at what hour people ride. A table with one row for each city each day has already added everything up, and answers almost nothing. So the first decision for every table is what one row stands for. Data specialists call this the grain of the table. Today it decides whether the churn KPI can be calculated at all.

Why the churn KPI needs a second database, a data warehouse

The point. Today's KPI, monthly churn by city and by plan, cannot be calculated from any of ÒRBITA's existing systems. ÒRBITA has to build one more database, a data warehouse, which copies data from all five systems into one place and organises it for adding up. Today your team designs that warehouse. This section explains why the existing systems are not enough.

What ÒRBITA's systems are built for. The billing system charges cards, pauses subscriptions and changes plans, thousands of times a day. Each of those actions touches one customer and a few rows. A database built for this kind of work is called operational (OLTP, online transaction processing). The telematics system, which records every ride, and the help desk, which records every support ticket, are operational databases too, each with its own data and its own customer numbers.

What a KPI needs. A KPI such as "monthly churn by city and plan for the last twelve months" needs every subscription of the last year, the rides of each customer from telematics, and the tickets of each customer from the help desk, all added up. That kind of work is called analytic (OLAP, online analytical processing): a few large questions, each reading millions of rows from several systems.

Three reasons the billing system cannot answer it:

  1. It does not contain the rides or the tickets. They are in other systems, which number the customers differently, so the rows cannot simply be matched.
  2. A question that reads millions of rows slows down the same machine that is charging customers' cards at that moment.
  3. Its columns follow billing's definitions, not the KPI's. For example, billing has 47,700 subscribers on its books in September because it counts paused, trial and unpaid accounts, while finance counts 40,100 paying subscribers on the same day (Session 1). The KPI counts paused accounts as paying and trial accounts as not paying, and billing does not know that rule.

So: ÒRBITA keeps the operational systems for running the business, and builds a warehouse for measuring it. The warehouse is filled every night from the five systems, with your team's definitions applied on the way. The rest of today decides what tables the warehouse contains.

Three kinds of data storage: warehouse, lake and lakehouse

Companies keep the data they analyse in one of three kinds of storage. The three differ in two ways: when someone checks that the data has the right structure, and who reads the data. The name of the software does not matter.

Data warehouseData lakeLakehouse
What it storesIt stores tables whose columns are fixed and documented.It stores files of any kind, exactly as they arrived: CSV, JSON, logs, images.It stores files in open table formats (Delta Lake, Apache Iceberg, Apache Hudi) on cheap cloud storage.
When the structure is checkedThe warehouse checks each row when it is loaded and rejects a row that does not fit. This is called schema on write.Nobody checks the files when they are stored. Whoever reads a file decides what it means. This is called schema on read.A control layer checks the structure of the files when they are written.
Who reads itSQL queries and dashboards read it: the numbers the board sees.Data scientists and engineers read it, often in Python.Both groups read it, from one copy of the data.
How it usually failsIt is slow and expensive to change when a new question arrives.After a while nobody knows what a file means or whether it is still current.It is newer and has more parts that must work together.

A schema is the list of the columns of a table and of what each column holds. The lakehouse is described in Armbrust, Ghodsi, Xin and Zaharia, Lakehouse: A New Generation of Open Platforms that Unify Data Warehousing and Advanced Analytics (CIDR 2021). Whichever kind ÒRBITA buys, your team answers the same design question in Step 2: what does one row of each table stand for?

✅ Step 2 · 15 min

Decide what one row of each table stands for

Why this step exists. Before a table has any columns, the designer decides what one row of it stands for: one ride, one customer in one month, one support ticket. That decision fixes which questions the table can ever answer. Data specialists call it the grain of the table, and write it as one sentence that starts "One row per…".

Your task. ÒRBITA wants its warehouse to answer the six questions in the list below. The list also shows six possible tables, each with a different row. Switch tables on until every one of the six questions has a ✓, and use as few tables as possible. Every extra table costs ÒRBITA storage and work, so the right answer is the smallest set that still answers all six.

The row counts are for one month of ÒRBITA: billing has 47,700 accounts on its books, customers make about 560,000 rides (about 14 per paying subscriber), the help desk receives about 3,800 tickets, and ÒRBITA runs ads in six cities on three channels.

ÒRBITA needs four tables, one for each activity that produces data

No single table answers all six questions. ÒRBITA has four activities that produce data, which data specialists call business processes: rides, subscriptions, support tickets and ad spending. Each one has its own natural answer to "what does one row stand for?": one row per ride, one row per account per month, one row per ticket, and one row per city, ad channel and week. The table with one row per account per day also answers the churn and retention questions, but it has thirty times as many rows as the monthly one; it is the right choice only if a question needs the day. The table with one row per city per day answers none of the six questions: once the rows are added up, the customer, the hour and the first fourteen days are gone, and no query can bring them back.

This is the rule from The Data Warehouse Toolkit (Kimball and Ross, 3rd ed., 2013): build one central table for each business process, with one row for the most detailed thing the process produces. The design follows four decisions in this order: choose the business process, decide what one row stands for, choose the describing columns, choose the numbers. Your team makes these four decisions in Step 4.

✅ Step 3 · 12 min · reading

Learn which columns hold numbers and which describe them

Do this: each member reads this step, which takes about 8 minutes, and sorts the eight columns at the end. The step counts when all eight are sorted correctly. Your team needs this step to draw its tables in Step 4.

Once the team has decided what one row stands for, every column of the central table is one of two kinds. A fact, also called a measure, is a number that the activity produces for that row, usually one you add up: kilometres ridden, minutes, euros of revenue, hours to resolve a ticket. A dimension is a description you use to filter and group the numbers: when, where, who, which plan, which ad channel. Each dimension has its own table (for example dim_city), with one row per city and columns that describe it. The central table, called the fact table, holds a key for each dimension: a number that points to the right row of that dimension table. When you draw it, the fact table sits in the middle and the dimension tables sit around it like the points of a star. That drawing is called a star schema.

Five more terms come with a star schema:

  • Date dimension. This is a table with one row for each calendar day. Its columns say the weekday, the month, the quarter, whether the day is a public holiday, and the financial period. Every fact table points to it, so "by month" or "without public holidays" becomes a filter, not a calculation.
  • Conformed dimension. This is a dimension that several fact tables share. dim_city and dim_date are used by both fact_ride and fact_spend, so you can put rides and ad spend per city per week in one chart. If the two tables spelled the cities differently, that chart would be impossible.
  • Surrogate key. The warehouse gives every row of a dimension table its own number, instead of reusing the customer number of one of the source systems. Telematics and billing can then use different numbers for the same customer, and the tables still join correctly.
  • Type 2 change (in a slowly changing dimension). When Anna Kowalski changes her email or her plan, the warehouse does not overwrite her row; overwriting is called type 1, and it loses the history. Instead it closes her old row with an end date (valid_to) and opens a new row with a start date (valid_from), so last month's rides stay linked to last month's plan.
  • Three kinds of fact table. A transaction table has one row per event, such as a ride. A periodic snapshot has one row per thing per period, such as an account per month, with its status on the 1st and whether it cancelled. An accumulating snapshot has one row per thing that moves through stages and is updated at each stage, such as a ticket that is opened, answered and resolved.

Say where every column comes from, what is done to it, and who is responsible for it

Why this step exists. Next week your team loads ÒRBITA's data into its tables. To do that, someone has to know, for every column of the warehouse, where its data is now: in which of ÒRBITA's five systems, and in which column of that system. For example, the date of a ride is not stored anywhere as a date: it comes from the column start_utc of the telematics system, and it has to be converted to the city's local time on the way. Session 1 showed the five systems and their columns: billing (subscriber_id, plan, status, status_since, mrr_eur), telematics (ride_id, subscriber_id, start_utc, end_utc, city, km), the support desk (ticket_id, email, category, opened, resolved_h), marketing (week, city, channel, spend, currency) and the finance spreadsheet (month, subscribers, mrr_keur, churn_pct). The table that says this is called a source-to-target map: the source is where the data is now, the target is the warehouse column it goes into. An auditor reads the same map when a number in a report changes. Its last three columns say who is responsible for the column (the owner), how sensitive the data is, and which check stops a wrong value from entering the warehouse.

How sensitive is a column?The GDPR, the EU's data-protection law, calls data that identifies a person personal data. A customer number that can be linked back to a person, such as subscriber_id or a scrambled email, is still personal data (GDPR Recital 26). ÒRBITA operates in the EU, so every personal column needs an owner and a stated purpose. Write Internal for business data that is not about a person, such as ad spend. Write Public for data that could be published as it is, such as the list of cities.

Five terms from today

  • OLTP and OLAP. An operational (OLTP) database runs the business with many small writes; an analytic (OLAP) database measures it with a few large reads. ÒRBITA needs both.
  • Schema on write and schema on read. A warehouse checks each row when it is loaded; a lake leaves the check to whoever reads the file.
  • Grain. The grain of a table is what one row stands for, written as a sentence that starts "One row per". The designer decides it first, because it fixes which questions the table can answer.
  • Star schema. A star schema has one central fact table for each business process, which holds the numbers, with a key to each describing table around it.
  • Source-to-target map. This table has one line for every warehouse column. Each line names the system and the column the data is copied from, the rule applied on the way, the manager responsible, whether the data is about a person, and the check that refuses a wrong value.
In Session 4 your team loads ÒRBITA's five data extracts into a star like yours and runs the checks from your map. What share of the rows will fail at least one check?
