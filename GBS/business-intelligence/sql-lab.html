Ask ÒRBITA's data warehouse questions in SQL: eight exercises that check their own answer

Why this page exists. In Session 3 your team designed ÒRBITA's warehouse as a star schema, and in Session 4 you chose the rules that load the data into it. A warehouse is only worth building if someone can ask it a question and get a number back. The language for that question is SQL (Structured Query Language), the language every warehouse, BI tool and data team uses. On this page you write SQL against a loaded copy of ÒRBITA's star and get the answer in a second.

How to use it.

  1. Read the tables below once, so you know what each one holds.
  2. Do the exercises in order: each one uses what the one before it taught.
  3. In each exercise, change the code in the grey box and press ▶ Run. The result appears under the box. When your result is the right one, the page writes Correct; otherwise it says what is different.
  4. The first Run loads the SQL engine into your browser (about 6 MB, once per visit). Everything runs on your own laptop: the code you type in the boxes is not sent anywhere.

Your code is kept in this browser, so you can close the page and come back. "Reset the code" in a box's top right corner puts the starting code back. Nothing on this page is graded.

The six tables in this warehouse

The data is invented for this lab: a random sample of 500 ÒRBITA accounts on 1 October 2026, with the same mix as Session 1's sample (84 % active, 9.5 % paused, 4 % trial, 2.5 % unpaid), plus the 34 accounts that signed up during October, and every ride these accounts took in October 2026: 6,908 rides. It is already loaded with good rules from Session 4: times are in local time, every city is spelled one way, failed unlocks are marked, and the ride of the unknown subscriber is set aside. The table holds no names and no email addresses.

A star schema is a warehouse design with one central table of events (the fact table, one row per ride) and, around it, tables that describe each event (the dimension tables: which day, which city, which subscriber, which vehicle). The fact table holds a key for each dimension: a number that points to one row of that dimension table.

The second fact table, fact_subscription, has one row per account for October (the "account-month" table of Session 3). It holds what the churn KPI needs.

Exercise 1 · SELECT, WHERE, ORDER BY

List the rides longer than 18 km, the longest first

Why. The head of fleet suspects that some riders take e-bikes far outside the city, which drains batteries and wears tyres. Before any rule is written, she wants to see the very long rides one by one.

WHERE keeps only the rows that meet a condition, for example WHERE km > 18. ORDER BY km DESC sorts the rows from the largest km to the smallest (DESC = descending; without it the order is ascending).

Your task

  1. Show two columns from fact_ride: ride_id and km, in this order.
  2. Keep only the rides with more than 18 km.
  3. Sort them so the longest ride is first.
SELECT ride_id, km FROM fact_ride -- write the WHERE line here ;
Exercise 2 · COUNT and SUM

Count the failed unlocks and all the rides in October

Why. A failed unlock is a customer standing next to a vehicle that will not open. Session 4 decided to keep these rows but mark them, so the fleet team can measure them. The first number the team asks for is how many there were, out of how many rides.

COUNT(*) counts rows. SUM(column) adds a column up. Because failed_unlock is 1 for a failed unlock and 0 otherwise, SUM(failed_unlock) counts the failed unlocks. AS gives a result column a name.

Your task

  1. Return one row with two columns: the number of failed unlocks, named failed, and the number of all rides, named rides.
  2. Use the whole of fact_ride, with no WHERE.
SELECT -- the number of failed unlocks AS failed, -- the number of rides AS rides FROM fact_ride;
Exercise 3 · GROUP BY

Find the five days of October with the most rides

Why. The operations team plans how many people move and charge vehicles each day. It wants to know which days were the busiest, to see whether they are weekdays and whether staff were short on those days.

GROUP BY date_key puts all rides of the same day into one group, so that COUNT(*) counts the rides of each day instead of all rides. Every column you show that is not inside COUNT or SUM must be in the GROUP BY.

Your task

  1. Show two columns: date_key and the number of rides on that day, named rides.
  2. Sort by rides, the busiest day first.
  3. Keep only the first five rows with LIMIT 5.
SELECT date_key, COUNT(*) AS rides FROM fact_ride -- group by the day, sort, and keep five rows ;
Show what weekday each date is
Run SELECT * FROM dim_date in the first box of the page. Exercise 5 lets SQL look this up for you, with a join.
Exercise 4 · JOIN one dimension

Count the rides and the kilometres in each city, with the city's name

Why. fact_ride knows a city only as a number (city_key), and a board member does not know that 4 is Milan. A join fetches the matching row of a dimension table for every fact row, so the result can show the name. This is the reason a star schema has dimension tables at all.

FROM fact_ride r JOIN dim_city c ON r.city_key = c.city_key puts, next to each ride, the row of dim_city with the same key. r and c are short names (aliases) for the two tables, so c.city_name means "the column city_name of dim_city". ROUND(x, 1) rounds to one decimal.

Your task

  1. Show three columns: city_name, the number of rides named rides, and the total kilometres rounded to one decimal, named km.
  2. Group by the city's name.
  3. Sort by rides, the city with the most rides first.
SELECT c.city_name, COUNT(*) AS rides -- add the total km, rounded to one decimal, AS km FROM fact_ride r JOIN dim_city c ON r.city_key = c.city_key -- group and sort ;
Exercise 5 · JOIN two dimensions

Compare e-bikes and scooters on weekdays and at weekends

Why. ÒRBITA is deciding which vehicles to buy for 2027. If e-bikes are used for longer rides and at weekends, the mix should change. The question needs two dimensions at once: the vehicle (from dim_vehicle) and the kind of day (from dim_date). A star answers it with two joins from the same fact table.

Two joins are written one after the other. Failed unlocks are not rides, so leave them out with WHERE r.failed_unlock = 0; otherwise the zeros pull the average down. AVG(x) is the average.

Your task

  1. Join fact_ride to dim_vehicle (on vehicle_key) and to dim_date (on date_key).
  2. Leave out the failed unlocks.
  3. Show four columns: vehicle_type, is_weekend, the number of rides named rides, and the average km rounded to two decimals, named avg_km.
  4. Group by the vehicle type and by is_weekend. The result has four rows.
SELECT v.vehicle_type, d.is_weekend, COUNT(*) AS rides -- add the average km AS avg_km FROM fact_ride r JOIN dim_vehicle v ON r.vehicle_key = v.vehicle_key -- join dim_date, leave out the failed unlocks, group ;
Exercise 6 · the churn KPI by city

Calculate October's churn by city with the definition from Session 3

Why. This is the KPI your team built the warehouse for in Session 3: monthly churn by city. Its contract says: the accounts paying on the 1st are the active and paused accounts (trial and unpaid are left out); a churned account is one of these that cancelled during the month, unless the cancellation was taken back within 30 days; churn is churned ÷ paying on the 1st, in %. Billing has no city, so the city comes from dim_subscriber.home_city_key.

COUNT(*) FILTER (WHERE …) counts only the rows that meet a condition, inside one group. status_on_1st IN ('active','paused') is true when the status is one of the two. Multiply by 100.0, not 100, so that SQL divides with decimals.

Your task

  1. Join fact_subscription to dim_subscriber (on subscriber_key) and dim_subscriber to dim_city (on home_city_key = city_key).
  2. Show four columns per city: city_name, paying_on_1st, churned, and churn_pct rounded to two decimals.
  3. Sort by churn_pct, the highest first.
SELECT c.city_name, COUNT(*) FILTER (WHERE f.status_on_1st IN ('active','paused')) AS paying_on_1st, COUNT(*) FILTER (WHERE /* paying on the 1st, cancelled, not taken back */ ) AS churned, ROUND(100.0 * churned / paying_on_1st, 2) AS churn_pct FROM fact_subscription f JOIN dim_subscriber s ON f.subscriber_key = s.subscriber_key -- join dim_city on the home city, group, sort ;
Show why churned can be reused on the next line
DuckDB, the engine on this page, lets a column named in SELECT be used again later in the same SELECT. Many other databases (PostgreSQL, SQL Server) do not: there you write the two COUNT expressions again inside ROUND.
Exercise 7 · a window function

Name the three subscribers who rode the most kilometres in each city

Why. Marketing wants to invite the three heaviest riders of each city to a "city ambassador" programme. A plain GROUP BY gives one total per subscriber, but it cannot number them inside each city. A window function can: it calculates a value for each row while looking at a group of rows (the "window"), without merging the rows into one.

RANK() OVER (PARTITION BY c.city_name ORDER BY SUM(r.km) DESC) gives 1 to the subscriber with the most km in each city, 2 to the next, and starts again at 1 in the next city. PARTITION BY says where the numbering restarts. A window function cannot be used in WHERE, so the query is wrapped: the inner query ranks, the outer one keeps the ranks 1 to 3.

Your task

  1. In the inner query, show city_name, subscriber_key, the subscriber's total km in that city rounded to one decimal named km, and the rank named rnk. Group by the city's name and the subscriber.
  2. In the outer query, keep the rows with rnk <= 3. The result has 18 rows: three per city.
SELECT * FROM ( SELECT c.city_name, r.subscriber_key, ROUND(SUM(r.km), 1) AS km, RANK() OVER (/* restart in each city, most km first */) AS rnk FROM fact_ride r JOIN dim_city c ON r.city_key = c.city_key GROUP BY c.city_name, r.subscriber_key ) -- keep the first three of each city ORDER BY city_name, rnk;
Exercise 8 · the secondary KPI

Count the rides that new subscribers took in their first 14 days, by the channel that brought them

Why. The secondary KPI of Session 3 is rides in the first 14 days: a subscriber who rides often in the first two weeks is less likely to cancel later. Marketing pays for Meta, Google and TikTok and wants to know which channel brings subscribers who actually ride. The trap in this question: a new subscriber who never rode must still be counted, with 0 rides. A plain JOIN drops them; a LEFT JOIN keeps every row of the first table even when the second has no match.

The query is written in two named steps with WITH (a common table expression): new_subs lists the subscribers who signed up from 1 to 18 October (so that all 14 days fall in October), and ride_days gives each ride its date from dim_date. A ride counts if its date is between the signup day and 13 days later: the signup day plus 13 more days make 14 days.

Your task

  1. Complete the last part: join new_subs to ride_days with a LEFT JOIN on the subscriber and on the date window.
  2. Show four columns per channel: signup_channel, new_subscribers (distinct subscribers), rides (count the ride_id, which is empty for a subscriber with no ride), and rides_per_subscriber rounded to two decimals.
  3. Sort by signup_channel.
WITH new_subs AS ( SELECT s.subscriber_key, s.signup_channel, s.signup_date FROM dim_subscriber s JOIN fact_subscription f ON f.subscriber_key = s.subscriber_key WHERE f.status_on_1st IS NULL -- signed up during October AND s.signup_date <= DATE '2026-10-18' ), ride_days AS ( SELECT r.ride_id, r.subscriber_key, d.date FROM fact_ride r JOIN dim_date d ON r.date_key = d.date_key ) SELECT n.signup_channel, COUNT(DISTINCT n.subscriber_key) AS new_subscribers -- add rides and rides_per_subscriber FROM new_subs n -- LEFT JOIN ride_days rd ON … AND rd.date BETWEEN n.signup_date AND n.signup_date + 13 GROUP BY n.signup_channel ORDER BY n.signup_channel;
