The model nobody can audit

Laptop with Microsoft Excel, the desktop app, open and working. The browser version cannot do tonight's keyboard work.

The session opens with a valuation model of Meridia Cold that looks finished and is wrong in twelve places: hardcodes inside formulas, inputs living in six places, a hidden plug, a sign error, no way to check anything. Twenty minutes to find as many as possible is the diagnosis. The rest of the session is the cure: how Excel actually calculates and why that decides how a model must be laid out, the layout and colour conventions the industry uses, the check row, and the keyboard habits that make the next ten weeks faster. The session ends with a blank model, correctly structured, with its first check row — the file every later session builds on.

The autopsy

The file is a six-year model of Meridia Cold — three historical years, three forecast years, a discounted cash flow and a value per share — as it might arrive from a colleague who left. It opens in Excel with no macros and no external links.

Instructions

1. Download and open meridia-cold-v7-FINAL-2.xlsx. 2. Twenty minutes, alone. Every fault is something a formula, a cell or the layout does that a reader would not expect — a hardcode, a duplicate, a wrong reference, a sign, a unit, a hidden thing, a missing thing. 3. Record each one as cell · what is wrong, one per line. 4. Seal the list before the room compares notes.

Tools that find faults faster than reading: Ctrl+` shows every formula instead of its result; Ctrl+G → Special → Constants selects every typed number, so a number inside a calculation block is a hardcode; Ctrl+[ jumps to what a cell depends on; Ctrl+\ on a selected row highlights the cells whose formula differs from the first one; the row numbers in the margin reveal a hidden row by skipping; a number that sits left-aligned in a column of right-aligned numbers is text. Mac equivalents are in Step 3.

One per line: the cell, then what is wrong. "E5 · text, not a number" is enough.

The twelve, and what each one did to the answer

The sheet reports an enterprise value of €249.0 m, equity of €192.0 m and a value per share of €0.0048. With the same inputs and the faults removed, the model gives EV €159.4 m, equity €99.4 m and €2.48 a share. The faults did not cancel out; they never do.

1E5 FY2025 revenue is stored as text ("180.4", left-aligned). Arithmetic coerces it, so the growth row looks fine; SUM ignores it, so the historical total in C17 reads 331.2 instead of 511.6. type
2F5:G5 grow revenue by *1.067 typed inside the formula; H5 uses the input $K$8. One row, two methods — changing the assumption changes one year in three. hardcode
3F7 EBITDA margin is 0.161 in the formula, G7 uses K9, H7 uses 0.17. FY2028 EBITDA is 37.3 instead of 35.3 because somebody tested a number and left it. hardcode
4Tax: 0.25 in four formulas, the input K10 (24%) in two, a text cell saying "Tax 25%", and 25% again on the Notes sheet. Four homes for one number, three values. duplicate
5H12 FY2028 capex is =G12 — a copy of the previous year instead of the row's formula. Capex stops growing with revenue in the year that drives the terminal value. reference
6F14 free cash flow adds capex: =F11+F8+F12-F13. FY2026 cash flow shows 40.2 against 9.6; it alone adds about €28 m to the present value. sign
7Row 15 is hidden and holds 2.5 in H15, which H14 adds to FY2028 cash flow. A plug that lifts the terminal value by 11%. The Notes sheet knows: "unhide adj row before sending??" hidden
8C19 holds the WACC, 8.5%, and nothing refers to it. Every discount formula uses 0.09, typed; D19 says "9% per CFO email". The visible input is not the one in use. hardcode
9H22 discounts FY2028 with ^2; it is year 3. reference
10Net debt is 57 in C26 and 60.0 on the Notes sheet, "bank statement 31/12". Two values, no link, no date on the one in use. duplicate
11C28 shares are in thousands (40,000); equity is in €m; C29 divides one by the other. €0.0048 a share is a unit error, not a valuation. units
12No check anywhere: nothing on the sheet says whether the statements tie, the sources match the uses, or the timeline is consecutive. The file name says "FINAL (2)" instead. no check
The patternNot one of the twelve is an arithmetic mistake. Each is a structural habit: a number where a reference belongs, an input with more than one home, a row that differs from its neighbours, a value whose unit is not written next to it, a thing nobody can see. A reader cannot find them by checking the arithmetic; they are found by checking the structure — which is what the conventions in Step 3 exist for.

The cure: how Excel calculates, and the conventions that follow from it

A · The engine

The dependency graph and the calculation chain

When a formula is entered, Excel parses its references and records them in a dependency graph: for every cell, which cells it reads (precedents) and which cells read it (dependents). From the graph it builds a calculation chain, an ordering in which every cell is computed after the cells it depends on. On each change only the cells downstream of the change are marked dirty and recomputed — smart recalculation — which is why a 50,000-formula model updates instantly after one input is edited. Ctrl+[ and Ctrl+] walk this graph; the Trace Precedents arrows draw it. A number typed inside a formula is invisible to the graph: it has no precedent cell, so no arrow points at it and no audit finds it by tracing.

Volatile functions, and why they are avoided

NOW, TODAY, RAND, OFFSET, INDIRECT, CELL and INFO are volatile: Excel recomputes them, and everything downstream, on every recalculation, because their result can change without any precedent changing. A model with OFFSET in its timeline recalculates whole on every keystroke. INDIRECT and OFFSET also build references from text, so the dependency graph cannot see them and tracing stops. This course uses INDEX/MATCH and CHOOSE, which are not volatile and are traceable; Session 2 is about them.

Relative, absolute and mixed references

A reference is stored as an offset from the cell that holds it: =C5*1.067 in F5 means "the cell three to the left, times 1.067". Copying the formula copies the offset, which is what makes one formula fill a row. A $ freezes one coordinate: $K$8 is always K8; K$8 keeps the row and lets the column move; $K8 the reverse. F4 (Mac: ⌘T) cycles a reference through the four forms. The row in the broken model mixed two: the first two cells carried no reference at all, the third an absolute one. A row built from one formula, filled right, cannot do that — and Ctrl+\ proves it in a second by highlighting any cell whose formula differs from the first.

Numbers, text and what aggregation ignores

A cell has a type. "180.4" typed into a cell formatted as Text, or pasted from a web page, is a string. In =E5/D5 Excel coerces the string to a number and the formula works, which is why the fault survives; SUM, AVERAGE and SUMPRODUCT skip text, which is why the total is wrong and nothing warns. Text numbers sit left-aligned and carry a green triangle; =ISTEXT() finds them; =VALUE() or Data → Text to Columns converts them.

Circular references

If cell A depends on B and B on A, the calculation chain has no valid order. Excel reports a circular reference and, with iterative calculation off (the default), returns 0 for the cycle. Interest on average debt creates exactly this cycle in Session 4; it is handled there by a switch, never by turning iteration on and hoping.

B · The layout convention

The conventions below are the common ground of the published modelling standards (the FAST standard — Flexible, Appropriate, Structured, Transparent — and the banking-school conventions taught by Wall Street Prep, Macabacus and Training the Street). They are not style; each one exists because of something in part A.

  • Inputs, calculations, outputs — separated. Three sheets, or three vertical blocks. Every number a human typed lives in Inputs and nowhere else; Calc contains formulas only; Outputs contains what the reader sees. Ctrl+G → Special → Constants on the Calc sheet must select nothing.
  • Time runs across, and the same column is the same period on every sheet. Column F is FY2023 on Inputs, Calc and Outputs alike. A formula can then be checked by position, and a timeline row at the top of every sheet is linked, not retyped.
  • One formula per row, written once in the first period column and filled right. A row that needs two formulas is two rows. Period flags (1 for an actual year, 0 for a forecast) turn the "if historical then input else formula" case into one formula: =flag×input + (1−flag)×calculation.
  • One input, one home. An assumption is typed once, in Inputs, with its unit and its source in the cells beside it, and referenced everywhere else. Net debt had two homes in the broken model and the tax rate four.
  • Units in a column, signs stated once. A units column (€m, %, days, x) next to every label; every row in the stated unit; costs shown as positive numbers that formulas subtract, or as negatives that formulas add — one convention per model, written on the cover.
  • Nothing hidden. No hidden rows or columns, no merged cells, no white text. Rows that clutter are grouped (Shift+Alt+→), which a reader can see and open.
  • Checks are rows, not opinions. A check is a difference that must be zero, computed in the model, aggregated into one master cell on the cover. Section D.

C · The colour convention

Four font colours, applied by what a cell is, not by what it looks like. The reader learns them once and then audits by colour: a blue cell on the Calc sheet is a hardcode; a black cell on Inputs is a formula where a typed number belongs.

Blue — 0000FFInputs: a number a human typed. Only on the Inputs sheet.
BlackFormulas on the same sheet.
Green — 008000Links to another sheet in the same file.
Red — C00000Links to another file (avoid), and the check block's warnings.

Excel's own tools apply it: Format → Cell Styles can hold the four as named styles; Ctrl+G → Special → Constants then font colour blue colours every hardcode in one move, and Special → Formulas colours every formula black.

D · The check row

A check compares two things the model computes separately and that must agree: the two sides of a balance sheet, sources against uses, the cash on the balance sheet against the cash-flow statement's closing cash, a timeline against the one it was linked from. It is written as a difference, aggregated so that one cell summarises all of them, and surfaced where the reader looks first:

check = ABS(a − b)  ·  passes when < 0.001  ·  master = IF(MAX(all checks) < 0.001, 0, 1)  ·  cover = IF(master = 0, "OK", "ERROR")

Tolerance, not equality: floating-point arithmetic leaves differences of 10⁻¹² between two routes to the same number, and =a=b would report them as errors. A check row lives on the sheet it checks, visible, and every check is also listed on a Checks sheet. A model whose master check is not 0 is not sent to anyone.

Teams and roles

Teams of three, fixed for the term; the final presentation is the team's, the participation mark is each member's own, and the file each student builds is their own. In each session every member takes one of three roles; the roles rotate:

  • Builder: hands on the keyboard for the team's shared decisions; responsible for the team producing its file.
  • Auditor: reads formulas, not results; runs the constants audit and the check rows on the Builder's file before anything is handed in.
  • Presenter: explains the model's result and the three assumptions it depends on, in plain sentences, to whoever asks.

Open question · for Session 2
"Of the twelve faults in the broken model, how many would a check block catch — and how many can only be caught by a convention?"
A check compares two computed numbers; it catches a model that does not tie (faults 1, 6, 7, 9, 11 would move a check somewhere). A hardcode or a duplicate input (2, 3, 4, 8, 10) keeps every check at zero and is caught only by the layout and colour discipline.
