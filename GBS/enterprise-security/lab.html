The arsenal, live in a terminal

Session 4 puts each weapon on the page as a gadget you click. This lab runs four of them for real, in Terminal, so the class watches the actual commands and output. Each one shows an attack and then the single change that stops it. The point the students keep is not the trick; it is that the defence is small, specific and known.

Students can also run these without a terminal: the same four as click-to-run demos in the browser →

The one rule, and say it out loud. Every target in this lab is this laptop. Nothing connects to the internet — the connection demo talks to 127.0.0.1, the loopback address that never leaves the machine. You run demonstrations like these only against systems you own or have written permission to test. That boundary is the professional lesson as much as any weapon on the page.

Before you start

  • Open Terminal (⌘-Space, type "Terminal"). macOS already ships Python 3 — nothing to install.
  • Make the font large before you share your screen: ⌘ + a few times.
  • Go to the lab folder:
    # wherever you keep the site, then: cd GBS/enterprise-security/lab
  • Run the "broken" version of each demo first. Let it land. Then run the defended version.
  • The four files are below each section as downloads; they are plain, commented Python — the reading is part of the lesson.

1 · Weak passwords — and the three things that stop guessing

One account, a human-chosen password. The attacker tries a short list of the most common weak passwords. First with no defences, then with a slow hash and a lockout.

python3 demo1_passwords.py # defences off → the password is found python3 demo1_passwords.py --defended # same guesses → locked out at 5
try 11: Summer2023 no try 12: Spring2024 no try 13: Summer2024 OK <== MATCH >> Cracked in 13 guesses, 2.00 s. --defended: try 5: admin no >> Account LOCKED after 5 wrong tries. Real password was never found.
The lessonThe guessing is identical in both runs. Only the victim's settings change. You cannot stop an attacker from guessing — you make each guess cost more and cap how many they get.
The defenceA slow, salted password hash; a lockout or rate-limit after a few wrong tries; and passwords long enough that a common-word list never contains them.

2 · A stolen password file — why storage is the whole game

A breach hands the attacker the hashes, not the passwords. How fast they turn hashes back into passwords depends only on how the defender stored them. This times it on the laptop in the room.

python3 demo2_hashing.py # about ten seconds
fast hash (SHA-256) 1,431,084 guesses / second slow hash (PBKDF2 200k) 11 guesses / second The slow hash is about 130,297x harder to guess through.
The lessonSame stolen file, same attacker, same laptop. The defender's one choice — a fast hash or a slow salted one — moves the answer by roughly a hundred thousand times.
The defenceNever store passwords in the clear or under a plain fast hash. Store them salted, under a deliberately slow hash (PBKDF2, bcrypt, scrypt, Argon2), with the work factor turned up.
⬇ demo2_hashing.py

3 · What "a connection" actually is

Two terminals side by side on the screen. One waits for a call; the other calls out; text passes between them. A command-and-control beacon — the thing malware opens once it lands — is, mechanically, exactly this socket.

Terminal 1 · the machine that waits
python3 demo3_connection.py listen
Terminal 2 · the machine that calls out
python3 demo3_connection.py connect
[listener] a connection arrived from 127.0.0.1:54049 them > hello from the beacon them > second line
The lessonThe only difference between this harmless chat and a weapon is whether the far end is wired to a shell. This lab deliberately does not do that — that is the line between a demonstration and an attack tool, and naming it is half the lesson.
The defenceThe malicious part is not clever; it is one outbound connection. So the defences watch the connection itself: egress firewall rules (which machines may call out, and to where) and EDR that flags a document viewer suddenly opening a socket.
⬇ demo3_connection.py

4 · SQL injection — one apostrophe walks past the login

The same attacker input runs two ways against a throwaway table built in memory: glued straight into the query, then passed as a parameter.

python3 demo4_sqli.py
Attacker's username : "' OR '1'='1' --" 1) VULNERABLE (username glued into the query): SELECT ... WHERE name = '' OR '1'='1' --' AND password = '...' >> LOGGED IN as: arvane_ops (operator) 2) FIXED (username passed as a parameter): SELECT ... WHERE name = ? AND password = ? params = ("' OR '1'='1' --", ...) >> rejected.
The lessonIn the first query the apostrophe ends the username and OR '1'='1' makes every row match, so the first user is logged in with no password. In the second the input is only ever data. One line of code is the entire difference.
The defenceNever build a query by pasting user input into a string. Pass input as parameters (prepared statements), so the database treats it as data and never as part of the command.
⬇ demo4_sqli.py

Close · put each one back on the kill chain

After the four demos, return to Session 4. Each weapon has a place on the chain: stolen passwords and injection are how the attacker gets in; the connection is how they stay and reach back out; the defences you just saw are where the chain breaks. The students have now watched the break happen, not just read that it can.
