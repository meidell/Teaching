Section 2.1 · Bloc 1

Enregistrer votre modèle dans un fichier qui porte une version

Pourquoi un fichier

Vendredi dernier, votre serveur a réentraîné votre modèle à chaque démarrage : il a lu 24 000 opérations, entraîné une forêt ou une régression, puis seulement il a commencé à répondre. Cela a trois défauts. Le démarrage est lent : le temps que GET / appelait duree_demarrage_s. Le résultat peut changer d’un démarrage à l’autre si les données ou une bibliothèque changent : deux serveurs peuvent répondre différemment à la même opération sans que personne le sache. Et personne ne peut dire quel modèle répond : il n’a pas de nom.

La règle en production : on entraîne une fois, on enregistre le modèle entraîné dans un fichier, on donne à ce fichier un numéro de version, et le service charge ce fichier. Ce fichier s’appelle un artefact : le résultat d’un entraînement, figé, que l’on peut copier, comparer et remettre en service. Vous en fabriquez un maintenant, avec votre modèle de vendredi.

Comment marchent les fenêtres de code
  • Comme vendredi : vous écrivez dans la fenêtre, vous cliquez sur ▶ Exécuter (ou Ctrl + Entrée), la page vérifie et dit ce qui manque. Les fenêtres de cette section partagent leurs variables : ce qui est créé dans l’une existe dans la suivante.
  • Les fenêtres 2 et 3 contiennent votre code de la journée 1 si vous l’avez écrit sur cet ordinateur, sinon la solution de référence. Dans les deux cas, lisez-le avant d’exécuter : c’est lui que vous allez enregistrer.
  • Le code écrit ici tourne dans votre navigateur. Il écrit des fichiers dans un disque qui n’existe que dans la page ; le bouton de l’étape 7 les télécharge sur votre ordinateur.

Étape 4 · à vous

Enregistrez l’artefact, puis rechargez-le et vérifiez qu’il répond pareil

Un artefact n’est pas seulement le modèle. Il emporte tout ce qu’il faut pour le servir et pour savoir d’où il vient : le modèle entraîné, le seuil de décision, la liste des variables dans l’ordre, un numéro de version, la date, les versions des bibliothèques. Mettez tout cela dans un dictionnaire et enregistrez-le avec joblib.dump. Le nom du fichier porte la version : modele-1.0.0.joblib.

Puis rechargez le fichier avec joblib.load, chronométrez ce chargement, et vérifiez que le modèle rechargé donne exactement les mêmes probabilités que celui qui est en mémoire sur toute la semaine de test. Enfin calculez l’empreinte du fichier : le SHA-256 de ses octets, un code de 64 caractères qui change dès qu’un octet change. C’est ainsi qu’un serveur prouvera plus tard qu’il sert bien ce fichier-là.

Étape 5 · à vous

Produisez une seconde version, puis tenez le registre et marquez celle qui est en production

En production, un modèle est remplacé plusieurs fois par an. Il faut donc savoir, à tout moment, quelles versions existent, ce que chacune vaut, et laquelle répond aux clients. Entraînez un second modèle qui diffère du premier par au moins une chose : un autre algorithme (forêt contre régression logistique), un autre nombre d’arbres, un autre seuil. (Une variable en plus demanderait aussi de refaire X_train et X_test : gardez cela pour chez vous.) Enregistrez-le dans modele-1.1.0.joblib.

Puis écrivez le registre : un fichier registre.json, une liste avec une entrée par version. Chaque entrée dit : la version, le fichier, son empreinte, la date, le seuil, le nombre de fraudes bloquées et de clients honnêtes bloqués sur la semaine de test à ce seuil, et le stade : "production" pour la version qui répond aux clients, "archive" pour les autres. Une seule version est en production. La fonction promouvoir(version) change de version en production et réécrit le fichier.

Remplacer votre serveur par un service qui charge le fichier

Pourquoi changer le serveur

Le serveur de la journée 1 contient modele.py, qui lit les données et entraîne à chaque démarrage, et app.py, qui l’importe. Vous allez remplacer les deux : un nouveau modele.py qui lit registre.json, charge le fichier marqué production et définit predire_v2() ; et un nouveau app.py, déjà écrit, qui dit dans GET / quelle version du modèle répond, son empreinte, et combien de temps a pris le démarrage. Les données n’ont plus besoin d’être sur le serveur.

L’hébergeur change. Hugging Face demande depuis novembre 2026 un abonnement payant pour créer un Space Docker. Le service d’aujourd’hui tourne sur Render, un hébergeur qui fait tourner gratuitement un petit service Python (512 Mo de mémoire) et lui donne une adresse publique ; il lit le code dans un dépôt GitHub, l’installe d’après requirements.txt et le relance à chaque fois que le dépôt change. Un service gratuit s’endort après 15 minutes sans appel et met environ une minute à se réveiller : vous allez mesurer cela aussi. Si votre Space de la journée 1 existe encore, un encadré à l’étape 9 dit comment le mettre à jour à la place.

Mettre à jour un service qui tourne est le moment le plus risqué de sa vie : selon l’hébergeur, il cesse de répondre pendant la reconstruction, ou bascule sans interruption. Vous allez mesurer ce qui se passe, à la seconde près.
