Programmer sans être programmeur : une vraie appli web en trois heures

Par équipes de deux ou trois, vous décrivez une application à un assistant IA gratuit, il écrit le code, vous le testez et le corrigez avec lui. À midi, votre appli est en ligne, elle garde ses données dans une base partagée, et le reste de la salle l’utilise sur son téléphone.

🎤 9h25Comment une IA écrit du code

Une page web, trois couches

Le navigateur reçoit un fichier texte et l’exécute. Ce fichier mélange trois langages, chacun avec un rôle :

  • HTML — la structure : un titre, un champ, un bouton, une liste. <button>Envoyer</button>
  • CSS — l’apparence : couleurs, tailles, disposition sur téléphone. button { background: teal; }
  • JavaScript — le comportement : ce qui se passe quand on clique. bouton.onclick = envoyer;

Aujourd’hui, les trois tiennent dans un seul fichier. C’est la forme la plus simple d’une application : pas de serveur à vous, pas d’installation.

Où vivent les données

Une page seule oublie tout quand on la ferme, et chaque utilisateur a sa propre copie. Pour qu’un message écrit sur un téléphone apparaisse sur un autre, il faut un endroit commun : une base de données sur Internet.

Nous utilisons Firebase Realtime Database (Google), dans sa version gratuite. Elle stocke un seul grand arbre JSON — des noms et des valeurs imbriqués :

{ "messages": {
    "-Nx81a": { "auteur": "Léa", "texte": "Bonjour !", "ts": 1793084400000 },
    "-Nx81b": { "auteur": "Omar", "texte": "Salut",    "ts": 1793084460000 } } }

Chaque branche a une adresse web. La page lui parle avec fetch(), en HTTP, le protocole du web : GET pour lire, POST pour ajouter, PATCH pour modifier, DELETE pour supprimer. C’est ce qu’on appelle une API REST. Le prompt 2 de l’atelier donne exactement ces quatre règles à l’IA.

Ce que fait réellement le modèle

Un assistant comme Claude ou ChatGPT est un grand modèle de langage. Il produit sa réponse un morceau de mot (un token) à la fois, en calculant à chaque pas quel token est le plus probable après tout ce qui précède — votre prompt compris. Il a appris ces probabilités sur une énorme quantité de texte, dont des millions de pages de code public.

Trois conséquences pratiques :

  1. Il est très bon sur ce qui est courant. Un formulaire, une liste, un bouton qui envoie des données : il a vu ces motifs des milliers de fois.
  2. Il ne connaît pas ce que vous ne lui dites pas. L’adresse de votre base, ce que « joli » veut dire pour vous, la règle qui refuse certaines écritures : si ce n’est pas dans le prompt, il le devine. D’où des prompts longs et précis.
  3. Il peut produire du code faux qui a l’air juste — une fonction qui n’existe pas, une condition inversée. Il ne l’exécute pas avant de répondre. C’est vous qui lancez, regardez, et lui rapportez l’écart.
Chat ou agent

Avec un assistant de chat, la boucle passe par vous : il écrit, vous copiez, vous lancez, vous lui recopiez l’erreur. C’est ce que nous faisons aujourd’hui — gratuit, dans le navigateur, et l’on voit chaque étape.

Un agent (Claude Code, Cursor, GitHub Copilot en mode agent…) fait la boucle seul : il crée les fichiers sur l’ordinateur, lance le code, lit les erreurs, corrige, recommence, et ne s’arrête que quand le résultat passe les tests. Ce sont en général des outils payants, pensés pour des projets de plusieurs fichiers.

🎤 Démonstration en direct

Un agent reçoit une seule consigne : « Construis un écran qui affiche en direct les résultats du sondage de ce matin, lus dans la base à cette adresse. » La salle suit à l’écran ce qu’il fait — les fichiers qu’il crée, les erreurs qu’il rencontre, les corrections qu’il apporte — jusqu’à l’écran qui fonctionne.

🛠 9h50Atelier 1 · La première version

  1. Formez une équipe de deux ou trois, un ordinateur. Ouvrez l’atelier et choisissez un nom d’équipe.
  2. Choisissez une idée — dans la liste ci-dessous ou la vôtre. Une idée qui tient en une phrase, avec trois fonctions concrètes. Petite et finie vaut mieux que grande et cassée.
  3. Copiez le prompt 1 dans l’assistant, copiez sa réponse dans l’atelier, cliquez ▶ Lancer.
  4. Testez chaque fonction. Ce qui ne marche pas : prompt 3, avec l’erreur, et ce que vous attendiez.

C’est fini quand : les trois fonctions marchent dans l’aperçu de l’atelier (les données disparaissent encore au rechargement : c’est normal à ce stade).

Quatre règles qui font gagner du temps
  • Une demande à la fois. Trois changements dans un prompt, et vous ne saurez pas lequel a cassé l’appli.
  • Toujours le fichier complet. Un morceau de code à « insérer quelque part » est la première source d’erreurs.
  • Décrivez l’écart, pas la solution. « J’ai cliqué sur Envoyer, rien n’apparaît, voici l’erreur » donne de meilleurs résultats que « corrige la fonction envoyer ».
  • Une version a cassé l’appli ? Le menu Versions de l’atelier ramène la précédente.

🛠 10h20Atelier 2 · La base de données

  1. Envoyez le prompt 2 dans la même conversation. Il contient l’adresse de la branche de votre équipe — l’IA ne peut pas l’inventer.
  2. Lancez, ajoutez un élément. Dans le panneau de droite, chaque requête à la base apparaît en vert ; un refus apparaît en rouge, avec son code.
  3. Regardez l’étape 4 de l’atelier : votre élément est dans la base, en JSON.
  4. Le test des deux appareils : ouvrez l’atelier sur un téléphone avec le même nom d’équipe, lancez la même version, ajoutez un élément d’un côté — il apparaît de l’autre.
Lire un refus

HTTP 401 veut dire : la base refuse cette écriture à cet endroit. Les règles de la base n’autorisent l’écriture que sur un élément précis de votre branche (…/messages/<id>), jamais sur la branche entière — sinon une seule requête pourrait effacer tout votre travail. Le prompt 2 le dit à l’IA ; si elle l’oublie, renvoyez-lui l’erreur avec le prompt 3.

C’est fini quand : un élément ajouté sur un appareil apparaît sur l’autre en moins de dix secondes, et il est toujours là après un rechargement.

🛠 11h05Atelier 3 · Améliorer, publier, tester

  1. Deux améliorations avec le prompt 4 — une à la fois, testée entre les deux.
  2. Publiez (étape 5 de l’atelier). Votre appli est dans la galerie, à une adresse que tout le monde peut ouvrir.
  3. Testez deux applis d’autres équipes sur votre téléphone. Pour chacune, notez une chose qui marche et une chose qui ne marche pas, et dites-la à l’équipe.
  4. Corrigez ce que l’on vous a signalé, et republiez.

🎤 11h30Ce qui peut mal tourner

Ce que vous venez de voir de vos propres yeux
  • La base de ce matin est ouverte. N’importe qui connaissant l’adresse peut lire et écrire dans la branche de n’importe quelle équipe — vous avez pu le faire. Une vraie appli exige une authentification (qui êtes-vous ?) et des règles côté base (qu’avez-vous le droit de faire ?). L’IA ne les ajoute pas si vous ne les demandez pas.
  • Tout le code d’une page web est public. Clic droit → « Afficher le code source ». Une clé secrète, un mot de passe, un tarif confidentiel écrit dans la page sont lisibles par tout visiteur.
  • Le texte des utilisateurs est dangereux. Affiché avec innerHTML, un message contenant du code est exécuté chez tous ceux qui le lisent (une attaque XSS). C’est pourquoi le prompt 2 impose textContent. Dans l’atelier, chaque appli tourne en plus dans un bac à sable isolé.
  • Les données personnelles ont une loi. En Suisse la nLPD, dans l’UE le RGPD : des noms, des téléphones ou des adresses dans une base exigent une raison, une information claire aux personnes, et un hébergement que vous savez justifier.
  • Un code qui marche n’est pas un code juste. Un calcul de dépenses peut afficher un résultat plausible et faux. Vérifiez les chiffres à la main sur un petit exemple.
Avant de confier une appli à de vrais utilisateurs
  1. Qui peut lire quoi, qui peut écrire quoi — et la base l’impose-t-elle vraiment ?
  2. Aucun secret dans le code de la page.
  3. Les données personnelles : lesquelles, pourquoi, combien de temps, où.
  4. Chaque fonction testée, y compris avec des entrées absurdes (vide, très long, émojis, deux clics rapides).
  5. Quelqu’un qui sait lire le code l’a relu — l’IA peut aider, elle ne remplace pas la relecture.

🏆 11h45Galerie et vote

Chaque équipe montre son appli à l’écran pendant une minute : ce qu’elle fait, et le prompt qui a été le plus utile. Ensuite, chacun vote dans la galerie — un ❤ par appli et par appareil.

Pour continuer seuls

Votre propre base Firebase, gratuite, en dix minutes
  1. Sur console.firebase.google.com, connectez-vous avec un compte Google et créez un projet.
  2. Dans le menu Build, choisissez Realtime Database → Create database, une région en Europe, et le mode test.
  3. Copiez l’adresse affichée en haut des données (elle finit par firebasedatabase.app) et mettez-la à la place de BASE dans votre fichier.

Le mode test laisse tout le monde lire et écrire, et Firebase le ferme de lui-même après quelques semaines. Pour une appli durable, demandez à l’IA de vous aider à écrire des règles de sécurité et à ajouter une connexion.

Mettre votre fichier en ligne

Le code de votre appli est dans l’atelier (étape 3) : copiez-le dans un fichier index.html. Ouvert d’un double-clic, il marche sur votre ordinateur. Pour une adresse publique, des hébergeurs gratuits pour pages statiques existent — GitHub Pages, Netlify, Cloudflare Pages, ou l’hébergement de Firebase lui-même. Demandez à l’assistant de vous guider pas à pas pour celui que vous choisissez.
